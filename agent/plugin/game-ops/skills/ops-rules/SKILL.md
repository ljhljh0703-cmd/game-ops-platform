# 분류 규칙 고치기

## 순서

1. `list_games` 로 게임을 보고, 게임마다 `corrections_summary` 를 부른다. 고친 기록이 없으면 「아직 근거가 없다」고 말하고 끝낸다.
2. `classifier_rules` 로 지금 규칙을 본다. 규칙은 위에서부터 먼저 걸리는 하나를 쓴다.
3. 자주 바뀐 쌍(예: `PAYMENT → UX` 3건)마다 원인을 찾는다.
   - 너무 넓은 키워드가 위쪽 규칙에 있다(예: 「결제」가 「결제 화면 글씨가 작아요」까지 잡음)
   - 빠진 키워드가 있다
   - 규칙 순서가 틀렸다
4. `rule_versions` 로 최근 반영 기록을 본다. 같은 수정이 이미 들어갔거나 사람이 되돌린 수정이면 다시 내지 않는다.
5. 수정안을 만든다. 키워드를 빼는 것보다 더 구체적인 규칙을 위에 추가하는 쪽을 먼저 고려한다. 바뀌는 키워드를 앞뒤로 보여 준다.
6. `apply_rule_change`(고친 뒤 규칙 전체, 이유) 로 낸다. 서버가 다시 시험해서
   - 통과하면 바로 반영되고 슬랙에 「🤖 분류 규칙을 고쳤어요 · ↩️ 되돌리기」 카드가 뜬다. 결과(dev 전→후, 바뀐 키워드)를 한 줄로 알린다.
   - 못 하면 이유가 온다(dev 하락, 회귀 문장 틀림, 결제·크래시 키워드 제거·심각도 하락). 이유를 보고 한 번 고쳐 다시 내거나, 사람에게 파일로 고치자고 제안한다.
7. 저장소가 열려 있으면 `./gradlew evalClassifier -Prules=수정안` 으로 미리 재 봐도 된다(서버 시험과 같은 기준). 반영된 규칙을 저장소 파일로 옮겨 커밋하는 건 사람이 정한다.

## 지킬 것

- 결제·강제 종료 규칙의 키워드를 빼거나 심각도를 낮추는 수정은 서버가 막는다. 필요하면 사람에게 파일로 고치자고 말한다.
- 평가 세트(`eval/classifier-cases.jsonl`)를 수정안에 맞춰 고치지 않는다. 정답을 바꾸려면 따로 사람 확인을 받는다.
- holdout(`-Pholdout=true`)은 수정안을 고르는 데 쓰지 않는다. 고를 때 보면 holdout 이 dev 가 된다.
- 결제 키워드를 좁히는 수정은 특히 조심한다. 점수는 오르는데 「결제가 두 번 됐어요」 같은 묶음 밖 결제 문장을 놓친 적이 있다(docs/stuck-notes.md 10). 놓친 문장을 찾으면 `eval/classifier-regression.jsonl` 에 더한다.
