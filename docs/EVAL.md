# 평가 하네스 — 분류와 묶기를 숫자로 고친다

자동 판단은 두 가지다. 제보 하나에 **분류·심각도**를 붙이는 일, 비슷한 제보를 한 이슈로 **묶는** 일. 둘 다 정답을 붙인 묶음으로 재고, 고친 뒤 다시 잰다.

```bash
./gradlew evalClassifier                                   # 지금 규칙
./gradlew evalClassifier -Prules=/tmp/새규칙.json -Plabel=후보  # 수정안
LLM_API_KEY=... ./gradlew evalClassifier -Pllm=true          # AI 분류(키가 있을 때만)
```

결과는 `eval/results/<날짜>-<이름>.md` 에 남는다(정확도, 분류별 정밀도·재현율, 헷갈린 표, 틀린 사례, 묶기 기준값 표).

## 1. 평가 묶음

| 파일 | 내용 | 나눔 |
|---|---|---|
| `eval/classifier-cases.jsonl` | 세 게임(젤리 패닉·보석타워·무브퓨) 제보 90건 + 정답 분류·심각도 | dev 60 / holdout 30 |
| `eval/duplicate-pairs.jsonl` | 제보 두 개 + 「같은 문제인가」 40쌍 | 같음 20 / 다름 20 |

- **dev 만 보고 고친다.** holdout 은 결과 문서에 틀린 사례도 적지 않는다. 고칠 때 보지 않은 글에서 몇 %인지가 「처음 보는 글」 성능이다.
- **함정 사례를 일부러 넣었다.** 「결제 화면 글씨가 작아요」(결제 낱말만 있고 돈 문제 아님), 「하트 충전이 안 돼요」(게임 안 충전), 「버튼을 눌러도 반응이 없어요」(버튼인데 버그).
- **한계: 묶음은 AI 가 쓴 초안이다.** 실제 플레이어 글이 아니고 정답도 한 사람 기준이다. 실제 제보가 쌓이면 그 글로 바꾸거나 더하고, 정답은 두 사람이 따로 붙여 맞춰 본다.

## 2. 분류: v1 → v2

| 규칙 | 분류 dev | 분류 holdout | 분류+심각도 dev | 분류+심각도 holdout |
|---|---|---|---|---|
| v1 (처음) | 65.0% | 50.0% | 63.3% | 50.0% |
| v2 | **98.3%** | **83.3%** | 98.3% | 83.3% |

v1 에서 틀린 21건을 셋으로 나눴다. 결과는 `eval/results/2026-10-20-v1-before.md`.

| 원인 | 예 | v2 에서 한 일 |
|---|---|---|
| 낱말 하나로 너무 넓게 잡음 | 「결제 화면 글씨」→ 결제, 「하트 충전」→ 결제 | 결제를 돈이 오간 표현(결제했, 충전했는데, 돈만, 환불해 …)으로 좁힘. 「결제하다 튕겼어요」는 계속 결제로(테스트로 고정) |
| 흔한 표현이 빠짐 | 「꺼져요」「검은 화면」「사라져요」「끼어요」 | 크래시·버그 키워드 추가 |
| 심각도 한 단계로는 부족 | 「세이브가 날아갔어요」가 버그·중간 | 진행 손실(날아갔, 초기화, 진행 불가)을 버그·높음 규칙으로 따로 |
| 순서 | 「버튼을 눌러도 반응이 없어요」가 불편 | 「반응이 없」을 버그에 넣어 불편보다 먼저 걸리게 |

**dev 98% 와 holdout 83% 의 차이(15%p)가 키워드 규칙의 한계다.** 처음 보는 표현은 놓친다. 다음 단계는 AI 분류를 같은 묶음으로 재서 그 차이를 메우는지 보는 것이다(키가 있어야 해서 아직 안 잼).

**관문:** `EvalGateTest` 는 기본 규칙의 분류 정확도가 dev 95%, holdout 80% 밑으로 떨어지면 실패한다. 운영 규칙 파일(`config/`)과 서버에 넣은 기본 규칙이 다를 때도 실패한다. 운영자나 에이전트가 규칙을 고쳐도 이 선 밑으로는 못 내려간다.

## 3. 묶기: 지금 기준이 거의 묶지 못한다

운영과 같은 정규화·유사도(글자 2개 묶음 자카드)로 기준값을 바꿔 가며 쟀다.

| 기준 | 묶음 정밀도 | 묶음 재현율 | 엉뚱하게 묶음 | 못 묶음 |
|---|---|---|---|---|
| 0.25 | 89% | 40% | 1 | 12 |
| **0.55 (지금)** | 50% | **5%** | 1 | 19 |
| 0.65 | 100% | 5% | 0 | 19 |

- 지금 기준 0.55 는 「보스 웨이브에서 튕겨요 / 보스웨이브에서 튕겨요ㅠ」 같은 거의 같은 글만 묶는다. 「로그인하면 바로 튕겨요 / 로그인 후 바로 튕김」(0.33)은 못 묶는다.
- 그런데 기준을 낮추면 「스테이지 3에서 게임이 튕겨요 / …느려요」(0.60)는 여전히 묶인다. 글자는 많이 겹치는데 증상이 다른 경우다(운영 설계서 S8).

후보 방식을 함께 쟀다. 잘못 묶이면 다른 문제가 한 이슈에 숨기 때문에 **「엉뚱하게 묶음 0건」을 지키는 기준**을 먼저 본다.

| 방식 | 엉뚱하게 묶음 0건인 기준 | 그때 재현율 |
|---|---|---|
| 자카드(지금) | 0.65 | 5% |
| **자카드 + 분류가 같을 때만** | 0.15 | **45%** |
| 겹침 계수 + 분류가 같을 때만 | 0.30 | 45% |

「분류가 같을 때만 묶기」 조건을 붙이면 「튕겨요/느려요」처럼 증상이 다른 쌍이 걸러져서 기준을 낮출 수 있다. 같은 문제를 묶는 비율이 5% 에서 45% 로 오른다.

**아직 운영에 넣지 않았다.** 평가 쌍이 40개뿐이고 같은 사람이 썼다. 넣기 전에 실제 제보로 한 번 더 확인해야 한다(운영 설계서 §8 P9, 작가 결정 대기).

## 4. 고리: 운영 → 고친 기록 → 수정안 → 평가 → 반영

1. 운영자나 AI 에이전트가 틀린 분류를 고친다. 고친 기록이 쌓인다(`/api/corrections/summary`).
2. 플러그인 `ops-rules` 스킬이 자주 틀리는 방향을 보고 규칙 수정안을 만든다.
3. `./gradlew evalClassifier -Prules=수정안` 으로 전후를 잰다. 떨어지면 버린다.
4. 사람이 승인하면 `config/classifier-rules.json` 에 저장한다. 다음 제보부터 반영되고, 관문 테스트가 바닥값을 지킨다.
