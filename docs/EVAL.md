# 평가 하네스 — 분류와 묶기를 숫자로 고친다

자동 판단은 두 가지다. 제보 하나에 **분류·심각도**를 붙이는 일, 비슷한 제보를 한 이슈로 **묶는** 일. 둘 다 정답을 붙인 묶음으로 재고, 고친 뒤 다시 잰다.

```bash
./gradlew evalClassifier                                   # 지금 규칙
./gradlew evalClassifier -Prules=/tmp/새규칙.json -Plabel=후보  # 수정안
LLM_API_KEY=... ./gradlew evalClassifier -Pllm=true          # AI 분류(키가 있을 때만)
```

결과는 `eval/results/<날짜>-<이름>.md` 에 남는다(정확도, 분류별 정밀도·재현율, 헷갈린 표, 틀린 사례, 묶기 기준값 표).

## 1. 평가 묶음

| 파일 | 내용 | 나눔 |
|---|---|---|
| `eval/classifier-cases.jsonl` | 세 게임(젤리 패닉·보석타워·무브퓨) 제보 90건 + 정답 분류·심각도 | dev 60 / holdout 30 |
| `eval/classifier-regression.jsonl` | 한 번 틀렸던 문장 17개(검토에서 나온 결제 문장 16 + 실제 디스코드 시험 1). 전부 맞아야 한다 | 회귀 |
| `eval/duplicate-pairs.jsonl` | 제보 두 개 + 「같은 문제인가」 40쌍 | 같음 20 / 다름 20 |

- **dev 만 보고 고친다.** holdout 은 결과 문서에 틀린 사례도 적지 않는다. 고칠 때 보지 않은 글에서 몇 %인지가 「처음 보는 글」 성능이다.
- **함정 사례를 일부러 넣었다.** 「결제 화면 글씨가 작아요」(결제 낱말만 있고 돈 문제 아님), 「하트 충전이 안 돼요」(게임 안 충전), 「버튼을 눌러도 반응이 없어요」(버튼인데 버그).
- **한계: 묶음은 AI 가 쓴 초안이다.** 실제 플레이어 글이 아니고 정답도 한 사람 기준이다. 실제 제보가 쌓이면 그 글로 바꾸거나 더하고, 정답은 두 사람이 따로 붙여 맞춰 본다.

## 2. 분류: v1 → v2 → v3

| 규칙 | 분류 dev | 회귀 16문장 | holdout | 결과 |
|---|---|---|---|---|
| v1 (처음) | 65.0% | 15/16 | 50.0% | `eval/results/2026-10-20-v1-before.md` |
| v2 (dev 틀린 사례만 보고 고침) | 98.3% | **1/16** | 83.3% | `…-v2.md` |
| v3 (검토 반영) | **100%** | **16/16** | 83.3% | `…-v3.md` |

**v1 → v2.** v1 에서 틀린 21건을 원인별로 나눴다.

| 원인 | 예 | 한 일 |
|---|---|---|
| 낱말 하나로 너무 넓게 잡음 | 「결제 화면 글씨」→ 결제, 「하트 충전」→ 결제 | 결제 키워드를 돈이 오간 표현으로 좁힘 |
| 흔한 표현이 빠짐 | 「꺼져요」「검은 화면」「사라져요」「끼어요」 | 크래시·버그 키워드 추가 |
| 심각도 한 단계로는 부족 | 「세이브가 날아갔어요」가 버그·중간 | 진행 손실을 버그·높음 규칙으로 따로 |
| 순서 | 「버튼을 눌러도 반응이 없어요」가 불편 | 「반응이 없」을 버그에 넣어 불편보다 먼저 |

**v2 의 실패.** 점수는 98% 였지만 코드를 쓰지 않은 검토자가 묶음 밖 실제 문장을 넣어 보니 「결제가 두 번 됐어요」「환불 해주세요」「결제 오류」가 결제로 안 잡혔다. 결제를 좁힌 대가로 가장 비싼 오류(결제 누락)를 늘린 것이다. dev 의 함정만 피하도록 고쳤기 때문이다(막힌 곳 10).

**v3.** 결제를 두 층으로 나눴다.
1. 돈이 오간 표현(결제했·두 번 결제·결제 오류·결제가 안·환불 요청·충전했는데 …) → 결제
2. 돈 문제가 아닌 경우를 먼저 걸러 냄: 「하트 충전」(게임 안 충전) → 버그, 「화면 글씨」 → 불편, 「어떻게 되나요·가격·비싸」 → 기타
3. 그다음 넓은 「결제·환불·충전」 → 결제

**실제 시험에서 하나 더.** 디스코드에서 처음 시험한 날 「화면이 이상함」이 기타·낮음으로 빠졌다(규칙에 「이상해」만 있었다). 「이상함·이상하」를 버그에 더하고 회귀 묶음에 넣었다. 묶음 밖 실제 글이 규칙의 빈틈을 바로 드러낸 예다.

**holdout 83% 와 dev 100% 의 차이가 키워드 규칙의 한계다.** 처음 보는 표현은 놓친다. 다음 단계는 AI 분류를 같은 묶음으로 재서 그 차이를 메우는지 보는 것이다(키가 있어야 해서 아직 안 잼).

**holdout 을 쓴 횟수를 밝힌다.** holdout 숫자는 v1·v2·v3 에서 세 번 봤다(틀린 사례 내용은 안 봄). 30건이라 1건이 3.3%p 이고, 같은 사람이 쓴 글이다. 그래서 「처음 보는 글 성능」의 대략치로만 본다. 이후로 평소 평가는 holdout 을 숨기고(`-Pholdout=true` 일 때만 보임), 실제 제보가 쌓이면 holdout 을 새 글로 바꾼다.

**관문.** `EvalGateTest` 가 막는 것:
- 기본 규칙의 분류 정확도가 dev 95%, holdout 80% 밑으로 떨어지는 경우
- 회귀 문장(한 번 틀렸던 문장, `eval/classifier-regression.jsonl`)이 하나라도 다시 틀리는 경우
- 운영 규칙 파일(`config/`)과 서버에 넣은 기본 규칙이 서로 다른 경우

**관문이 못 막는 것.** 서버는 `config/classifier-rules.json` 을 실행 중에 다시 읽는다. 운영자나 에이전트가 파일을 저장하면 테스트를 거치지 않고 바로 쓰인다. 그래서 `ops-rules` 스킬은 저장 전에 반드시 평가를 돌리게 하고, 저장한 파일은 깃에 커밋해 관문 테스트를 통과시킨다. 서버가 다시 읽을 때 평가 묶음으로 확인하는 것은 다음 할 일이다.

## 3. 묶기: 지금 기준이 거의 묶지 못한다

운영과 같은 정규화·유사도(글자 2개 묶음 자카드)로 기준값을 바꿔 가며 쟀다.

| 기준 | 묶음 정밀도 | 묶음 재현율 | 엉뚱하게 묶음 | 못 묶음 |
|---|---|---|---|---|
| 0.25 | 89% | 40% | 1 | 12 |
| **0.55 (지금)** | 50% | **5%** | 1 | 19 |
| 0.65 | 100% | 5% | 0 | 19 |

- 지금 기준 0.55 는 「보스 웨이브에서 튕겨요 / 보스웨이브에서 튕겨요ㅠ」 같은 거의 같은 글만 묶는다. 「로그인하면 바로 튕겨요 / 로그인 후 바로 튕김」(0.33)은 못 묶는다.
- 그런데 기준을 낮추면 「스테이지 3에서 게임이 튕겨요 / …느려요」(0.60)는 여전히 묶인다. 글자는 많이 겹치는데 증상이 다른 경우다(운영 설계서 S8).

후보 방식을 함께 쟀다. 잘못 묶이면 다른 문제가 한 이슈에 숨기 때문에 **「엉뚱하게 묶음 0건」을 지키는 기준**을 먼저 본다.

| 방식 | 엉뚱하게 묶음 0건인 기준 | 그때 재현율 |
|---|---|---|
| 자카드(지금) | 0.65 | 5% |
| **자카드 + 분류가 같을 때만** | 0.15 | **45%** |
| 겹침 계수 + 분류가 같을 때만 | 0.30 | 45% |

「분류가 같을 때만 묶기」 조건을 붙이면 「튕겨요/느려요」처럼 증상이 다른 쌍이 걸러져서 기준을 낮출 수 있다. 같은 문제를 묶는 비율이 5% 에서 45% 로 오른다.

**아직 운영에 넣지 않았다.** 평가 쌍이 40개뿐이고 같은 사람이 썼다. 「분류가 같을 때만」 비교에 쓴 분류 규칙도 같은 사람이 dev 에 맞춰 고친 것이라 45% 는 낙관치다. 넣기 전에 실제 제보로 한 번 더 확인해야 한다(운영 설계서 §8 P9, 작가 결정 대기).

## 4. 고리: 운영 → 고친 기록 → 수정안 → 평가 → 반영

1. 운영자나 AI 에이전트가 틀린 분류를 고친다. 고친 기록이 쌓인다(`/api/corrections/summary`).
2. 플러그인 `ops-rules` 스킬이 자주 틀리는 방향을 보고 규칙 수정안을 만든다.
3. `./gradlew evalClassifier -Prules=수정안` 으로 dev 와 회귀 문장을 잰다. 떨어지거나 회귀가 하나라도 틀리면 버린다. 틀린 적 있는 문장은 회귀 묶음에 더한다.
4. 사람이 승인하면 `config/classifier-rules.json` 에 저장한다(다음 제보부터 반영). 깃에 커밋해 관문 테스트를 통과시킨다.
