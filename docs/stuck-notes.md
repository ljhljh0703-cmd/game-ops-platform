# 만들면서 막힌 곳

## 1. 같은 버그 제보 8건이 동시에 들어오면 일부가 실패했다
- 증상: 동시 접수 테스트에서 `ObjectOptimisticLockingFailureException`. 8건이 같은 이슈의 제보 수를 동시에 올리면서 version 충돌이 났고, 재시도 3회로는 모자랐다.
- 해결: 붙일 이슈를 찾은 뒤 그 행을 `PESSIMISTIC_WRITE` 로 잠가 차례로 줄 세웠다. 낙관적 잠금(version)은 상태 변경과의 충돌을 잡는 용도로 남겼다.
- 배운 것: 경합이 드문 곳은 낙관적 잠금, 한 행에 쓰기가 몰리는 곳(인기 이슈 카운터)은 비관적 잠금.

## 2. 잠금 쿼리를 따로 만들었는데도 같은 에러가 났다
- 증상: `select … for update` 를 하는 리포지토리 메서드를 추가했지만 여전히 version 충돌.
- 원인: 같은 트랜잭션에서 이미 그 이슈를 읽어 영속성 컨텍스트(1차 캐시)에 들고 있었다. 잠금 쿼리는 DB에 나갔지만 Hibernate는 캐시에 있던 옛 객체를 돌려줬고, 옛 version으로 저장하다 충돌했다.
- 해결: `EntityManager.refresh(entity, PESSIMISTIC_WRITE)` 로 잠그면서 DB 최신 값으로 다시 읽었다. 잠근 뒤 이슈가 그사이 닫혔으면 붙이지 않고 새 이슈를 만든다.

## 3. 테스트용 PostgreSQL 컨테이너가 안 떴다
- 증상: `Could not find a valid Docker environment`. 로그를 보니 `client version 1.32 is too old. Minimum supported API version is 1.40`.
- 원인: Docker 29부터 오래된 API 버전을 거부하는데, 테스트 컨테이너가 쓰는 Docker 클라이언트가 기본으로 낮은 버전을 보냈다.
- 해결: `src/test/resources/docker-java.properties` 에 `api.version=1.44`.

## 4. (작업 환경 한정) 이미지 빌드 단계에서 의존성 내려받기 실패
- 증상: 이미지 안 Gradle이 `PKIX path building failed`.
- 원인: 개발에 쓴 클라우드 작업 공간은 외부 접속을 중계 서버로 보내고 그 서버의 인증서를 쓰는데, 빌드 컨테이너에는 그 인증서가 없다. 일반 개발 PC에서는 생기지 않는다.
- 처리: 이 환경에서는 jar를 밖에서 빌드해 실행 단계 이미지만 검증했다. Dockerfile 자체는 그대로 둔다.
- 확인(2026-10-19): 작가 맥에서 `start.command` 로 이미지 빌드부터 헬스체크 UP 까지 통과했다. 일반 PC에서는 이 문제가 없다.

## 5. 독립 검토에서 나온 버그 3건 (직접 못 잡은 것)
- 슬랙 서명이 실제 슬랙 요청에서는 틀리게 나올 뻔했다. 테스트가 서버와 같은 방식(자바 URLEncoder)으로 본문을 만들어서 통과했던 것이다. 테스트 자체가 실제 슬랙과 다른 입력을 쓰고 있었다. 원래 바이트로 서명을 계산하도록 고치고, 공백 `%20`·소문자 16진수로 보낸 요청이 통과하는 테스트를 넣었다.
- 닫힌 이슈를 다시 열 때, 같은 내용의 열린 이슈가 이미 있으면 DB 고유 인덱스에 걸려 500 이 났다. 409(충돌)로 돌려주게 했다.
- 링크·이모지만 있는 제보는 정규화하면 빈 글이 되는데, 빈 글끼리 유사도 1.0 으로 계산돼 전부 한 이슈로 묶였다.

## 6. 슬랙을 켜자 서버가 안 켜졌다 (작가 맥 첫 실연결)
- 증상: `required a single bean, but 2 were found: loggingSender, slackSender`.
- 원인: 「다른 전송기가 없으면 로그 전송기를 띄운다」는 조건이 설정 클래스를 읽는 순서에 따라 결과가 달라졌다. 테스트 환경에서는 슬랙을 켠 채 서버 전체를 띄워 본 적이 없어 못 잡았다. 독립 검토가 「순서에 기대고 있어 깨지기 쉽다」고 짚었던 곳이다.
- 해결: 슬랙 설정값(`gameops.slack.enabled`) 하나로 둘 중 하나만 뜨게 바꿨다. 설정 클래스 순서를 양쪽으로 바꿔도 전송기가 하나인지 확인하는 테스트를 넣었다.

## 7. 되돌리기·키워드 파일·재발·슬랙 버튼 추가 후 독립 검토에서 나온 것
- 사람이 심각도를 「낮음」으로 내려도, 비슷한 제보가 하나 더 붙으면 자동 올리기가 다시 「가장 높음」으로 돌려놓았다. 「불편/가장 높음」 같은 엉뚱한 조합에 긴급 알림까지 나갔다. 사람이 고친 이슈는 자동으로 올리지 않게 했다.
- 키워드 파일을 저장하는 도중에 읽으면 실패한 뒤, 완성된 파일이 같은 시각이면 다시 읽지 않았다. 실패한 뒤에는 다음 제보 때 내용을 다시 확인하게 바꿨다.
- 공개 주소를 못 받았을 때 실패 기록 속 `api.trycloudflare.com` 을 슬랙 주소로 잘못 안내할 수 있었다.
- 닫힌 이슈에서 떼어내기를 허용하면, 같은 글의 새 제보와 서로 잠금을 기다리다 DB가 한쪽을 끊어 500 이 날 수 있었다. 닫힌 이슈 떼어내기는 막고, 잠금 경합은 접수에서 다시 시도·API에서 409 로 돌려준다.
- 서버 포트가 같은 와이파이의 다른 기기에도 열려 있었다. 내 컴퓨터 안에서만 열리게 했다.
- 서버 컨테이너가 다시 만들어져 내부 주소가 바뀌면 슬랙 중계가 옛 주소로 보내 502 가 났다. 이름을 10초마다 다시 찾게 했다.

## 정리: 테스트는 통과했는데 실제에서 막힌 것들의 공통점
- 5번(슬랙 서명)과 6번(전송기 두 개)은 테스트 환경이 실제와 달랐던 곳이다. 테스트는 가짜 슬랙과 다른 설정 조합으로 돌았고, 실제 연결에서야 드러났다.
- 그래서 고칠 때마다 실제와 같은 입력·설정으로 다시 막히는지 확인하는 테스트를 함께 넣었다.
