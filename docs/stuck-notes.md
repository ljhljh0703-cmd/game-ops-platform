# 만들면서 막힌 곳

직접 부딪혀 고친 것과, 코드를 쓰지 않은 검토자가 찾아내 고친 것을 구분해 적었다. 항목마다 다시 막히지 않는지 확인하는 테스트를 함께 넣었다.

## 1. 같은 버그 제보 8건이 동시에 오면 일부가 실패했다 (직접)
- 증상: 동시 접수 테스트에서 `ObjectOptimisticLockingFailureException`. 8건이 같은 이슈의 제보 수를 동시에 올리면서 version 충돌이 났고, 재시도 3회로는 모자랐다.
- 해결: 붙일 이슈를 찾은 뒤 그 행을 `PESSIMISTIC_WRITE` 로 잠가 차례로 줄 세웠다. 낙관적 잠금(version)은 상태 변경과의 충돌을 잡는 용도로 남겼다.
- 판단: 경합이 드문 곳은 낙관적 잠금, 한 행에 쓰기가 몰리는 곳(인기 버그의 제보 수)은 비관적 잠금.

## 2. 잠금 쿼리를 따로 만들었는데도 같은 에러가 났다 (직접)
- 증상: `select … for update` 리포지토리 메서드를 추가했지만 여전히 version 충돌.
- 원인: 같은 트랜잭션에서 그 이슈를 이미 읽어 영속성 컨텍스트(1차 캐시)에 들고 있었다. 잠금 쿼리는 DB에 나갔지만 Hibernate는 캐시에 있던 옛 객체를 돌려줬고, 옛 version으로 저장하다 충돌했다.
- 해결: `EntityManager.refresh(entity, PESSIMISTIC_WRITE)` 로 잠그면서 DB 최신 값으로 다시 읽었다. 잠근 뒤 그사이 닫힌 이슈에는 붙이지 않고 새 이슈를 만든다.

## 3. 슬랙 서명 검사가 테스트에선 통과하고 실제 슬랙 요청에선 틀릴 뻔했다 (검토)
- 원인: 서명을 스프링이 다시 조립한 폼 본문으로 계산했다. 테스트도 서버와 같은 방식(자바 `URLEncoder`)으로 본문을 만들어서, 틀린 코드와 틀린 테스트가 서로를 맞다고 확인해 주고 있었다. 실제 슬랙은 공백을 `%20`, 16진수를 소문자로 보내 바이트가 달라진다.
- 해결: 요청 본문의 원래 바이트로 HMAC을 계산한다. 슬랙과 같은 인코딩으로 만든 요청이 통과하는 테스트를 넣었다.

## 4. 슬랙을 켜자 알림 전송기가 두 개 떠서 서버가 안 켜졌다 (실제 연결에서 발견)
- 증상: `required a single bean, but 2 were found: loggingSender, slackSender`.
- 원인: 「다른 전송기가 없으면 로그 전송기를 띄운다」(`@ConditionalOnMissingBean`)는 조건이 설정 클래스를 읽는 순서에 따라 결과가 달라졌다. 테스트에서는 슬랙을 켠 채 서버 전체를 띄워 본 적이 없어 못 잡았다.
- 해결: 슬랙 설정값 하나로 둘 중 하나만 뜨게 바꿨다. 설정 클래스 순서를 양쪽으로 바꿔도 전송기가 하나인지 확인하는 테스트를 넣었다.

## 5. 사람이 내린 심각도를 다음 제보가 다시 올려 버렸다 (검토)
- 증상: 「결제 버튼 위치가 헷갈려요」가 결제·가장 높음으로 잡혀 운영자가 불편·낮음으로 고쳤다. 비슷한 제보가 하나 더 붙자 자동 올리기가 다시 「가장 높음」으로 돌려놓고 긴급 알림까지 보냈다. 결과는 「불편/가장 높음」이라는 엉뚱한 조합.
- 원인: 「심각도는 자동으로 올리기만 한다」는 규칙과 「사람이 고칠 수 있다」는 기능을 따로 만들고, 둘이 만나는 경우를 정하지 않았다.
- 해결: 사람이 분류를 고친 이슈는 자동으로 올리지 않는다. 제보 수만 늘고 다시 올릴지는 사람이 정한다.

## 6. 닫힌 이슈에서 떼어내기와 새 제보 접수가 서로를 기다릴 수 있었다 (검토, 재현 안 함)
- 원인: 떼어내기는 닫힌 이슈 행을 `FOR UPDATE` 로 잠근다. 같은 때 새 제보가 그 이슈를 「재발 대상」으로 참조하며 들어오면, 외래 키 검사가 잠긴 행을 기다린다. 그 새 제보가 떼어내기가 쓰려는 고유 키를 먼저 잡고 있으면 서로를 기다리고, PostgreSQL이 한쪽을 끊어 500 이 난다.
- 해결: 닫힌 이슈 떼어내기는 막았다(다시 연 뒤에). 남은 잠금 경합은 접수에서 다시 시도하고, API에서는 409 로 돌려준다.

## 7. 빈 글끼리 유사도 1.0 으로 계산돼 무관한 제보가 한 이슈로 몰렸다 (검토)
- 원인: 링크·이모지만 있는 제보는 정리하면 빈 문자열이 되고, 빈 문자열끼리는 같은 글로 계산됐다. 스크린샷 주소만 올린 서로 다른 제보들이 한 이슈에 묶였다.
- 해결: 정리 후 남는 글자가 없으면 비교하지 않고 제보마다 따로 이슈를 만든다.

## 8. 서버를 여러 대 띄우면 주간 보고가 대수만큼 나갔다 (검토)
- 원인: 예약 작업은 서버마다 돈다.
- 해결: 예약 작업 잠금 라이브러리 대신, 대기열에 「게임+주」 키로 한 번만 넣는다. DB 고유 인덱스 하나로 해결했다.

## 9. 키워드 파일을 저장하는 도중에 읽으면 고친 규칙이 끝내 반영되지 않았다 (검토)
- 원인: 파일 수정 시각만 보고 다시 읽을지 정했다. 반쯤 저장된 파일을 읽어 실패한 뒤 완성본이 같은 시각으로 저장되면, 이미 본 파일로 여기고 다시 읽지 않았다.
- 해결: 시각과 크기를 함께 보고, 마지막 읽기가 실패했으면 다음 제보 때 내용을 다시 확인한다. 같은 내용으로 계속 실패하면 오류 기록은 한 번만 남긴다.

## 정리
- 3·4번은 테스트 환경이 실제와 달라서 생겼다. 고칠 때마다 실제와 같은 입력·설정으로 다시 막히는지 확인하는 테스트를 함께 넣었다.
- 5·6번은 기능을 하나씩 따로 맞게 만들어도, 두 기능이 만나는 지점에서 생긴 문제다. 검토를 맡길 때 「새 기능이 기존 규칙과 만나는 곳」을 따로 보게 했다.
