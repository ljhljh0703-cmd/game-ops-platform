# 운영 설계서 — 시나리오 · 분류 기준 · 판단 기준 · 책임과 위임

게임 운영 플랫폼이 플레이어 제보를 어떻게 받고, 무엇을 기준으로 나누고 묶고, 누가 어디까지 정하는지 적은 문서다. 문서의 모든 수치와 규칙은 현재 코드에 있는 값이다(근거 파일을 각 절 끝에 적었다).

---

## 1. 한 줄 요약

플레이어는 디스코드에 쓰기만 하고, 시스템은 받기·분류·묶기·알림·보고까지 자동으로 처리하며, 이슈를 닫는 결정은 사람만 한다.

```
플레이어 ──글──▶ 디스코드 봇 ──▶ 분류(AI 또는 규칙) ──▶ 중복 판단 ──▶ 이슈 DB
                    │                                              │
                    └──── 접수 답장(이슈 번호) ◀───────────────────┘
                                                                   │
                                          알림 대기열 ──▶ 슬랙(개발팀)
                                                                   │
                                         운영자 ──상태 변경──▶ 이슈 DB + 감사 기록
```

## 2. 예상 시나리오

### 2-1. 정상 흐름

| # | 상황 | 시스템 반응 | 플레이어가 보는 것 | 개발팀이 보는 것 |
|---|---|---|---|---|
| S1 | 처음 보는 버그 제보 「보스 웨이브에서 게임이 튕겨요」 | 크래시·높음으로 분류, 이슈 #1 생성, 알림 대기열에 기록 | 「접수했어요. 이슈 #1 로 개발팀에 전달합니다.」 | 긴급 채널에 「새 이슈 #1 · CRASH/HIGH · 제보 1건」 |
| S2 | 같은 버그를 다른 말로 「보스웨이브에서 튕김ㅠㅠ」 | 열린 이슈 #1과 비슷하다고 판단해 합침, 제보 수 +1 | 「비슷한 제보가 있어 이슈 #1 에 합쳤어요. 같은 제보 2건째입니다.」 | 새 알림 없음(같은 이슈 반복 알림 방지) |
| S3 | 다른 내용 「젤리 색깔이 비슷해서 헷갈려요」 | 불편·낮음으로 분류, 이슈 #2 생성 | 「접수했어요. 이슈 #2 …」 | 기본 채널에 새 이슈 알림 |
| S4 | 이미 있는 이슈에 더 심각한 제보가 붙음 (버그로 접수된 이슈에 「…하다가 튕겨요」) | 이슈 심각도를 올림 | 합쳤다는 답장 | 「심각도 상승」 알림 |
| S5 | 결제 문제 「결제했는데 보석이 안 들어왔어요」 | 결제·가장 높음으로 분류 | 접수 답장 | 긴급 채널에 즉시 알림 |
| S6 | 월요일 오전 9시 | 게임별 주간 보고 생성 | — | 신규·해결·미해결 건수와 제보 많은 미해결 상위 5건 |
| S7 | 운영자가 이슈를 해결 처리 | 상태 변경 + 누가 언제 바꿨는지 기록 | — | (API로 처리. 슬랙 버튼은 §7 참고) |

### 2-2. 예외·장애 흐름

| # | 상황 | 시스템 반응 | 왜 이렇게 했나 |
|---|---|---|---|
| E1 | 디스코드가 같은 메시지를 두 번 보냄 | 제보는 1건만 저장, 「이미 접수된 제보예요」 | 채널+메시지 번호 고유 제약. 서버를 여러 대 띄워도 지켜진다 |
| E2 | 같은 버그 제보 8건이 동시에 들어옴 | 이슈 1개, 제보 8건으로 정확히 묶임 | 붙일 이슈 행을 잠가 차례로 처리 (실제로 막혔던 문제, stuck-notes 1·2) |
| E3 | 슬랙이 죽어 있음 | 제보·이슈는 정상 저장. 알림은 2초·4초·8초·16초 간격으로 다시 보내고 5번 실패하면 실패로 표시해 남김 | 외부 서비스 장애가 접수를 멈추게 하지 않는다 |
| E4 | AI 분류가 응답이 없거나 엉뚱한 형식으로 답함 | 키워드 규칙으로 분류해 계속 진행 | 분류 정확도보다 접수가 끊기지 않는 쪽이 먼저 |
| E5 | 링크·이모지만 있는 글 (「ㅋㅋㅋ」, 스크린샷 주소만) | 비교하지 않고 따로 이슈 생성 | 빈 글끼리 묶이면 무관한 제보가 한 이슈로 몰린다 (독립 검토에서 발견) |
| E6 | 봇이 쓴 글 · 제보 채널이 아닌 곳의 글 | 무시 | 봇끼리 대화 고리, 잡담 수집 방지 |
| E7 | 이미 해결된 버그가 다시 제보됨 | 새 이슈로 생성 (닫힌 이슈에는 붙이지 않음) | 재발은 새 사건으로 본다. 단 「재발」 표시가 없는 점은 개선 과제(§8 P3) |
| E8 | 닫힌 이슈를 다시 열려는데 같은 내용의 열린 이슈가 이미 있음 | 409(충돌)로 거절, 새로고침 안내 | 같은 내용의 열린 이슈가 둘이 되는 것을 막는다 |
| E9 | 서버가 꺼져 있던 동안 올라온 글 | 수집하지 않음 | 현재 한계. 24시간 운영은 클라우드 이전 필요 |
| E10 | 슬랙 버튼 요청이 위조됐거나 5분이 지남 | 401로 거절, 상태 변경 없음 | 서명 확인 없이는 누구나 상태 변경 요청을 만들 수 있다 |

## 3. 분류 기준

분류기는 제보 하나에 분류 · 심각도 · 제목을 붙인다.

### 3-1. 키워드 규칙 (기본값, 외부 호출 없음)

위에서부터 먼저 걸리는 규칙 하나를 쓴다. 더 심각한 규칙을 위에 두었다.

| 순서 | 분류 | 심각도 | 걸리는 말 (일부) |
|---|---|---|---|
| 1 | 결제 PAYMENT | 가장 높음 CRITICAL | 결제, 환불, 충전, 구매했는데 |
| 2 | 크래시 CRASH | 높음 HIGH | 튕, 크래시, 강제 종료, 멈춤, 먹통, 접속 불가 |
| 3 | 성능 PERFORMANCE | 중간 MEDIUM | 렉, 느려, 프레임, 버벅, 로딩이 길 |
| 4 | 버그 BUG | 중간 MEDIUM | 버그, 오류, 안 돼, 이상해, 깨져 |
| 5 | 밸런스 BALANCE | 낮음 LOW | 밸런스, 너무 세, 너무 약, 너프, 버프 |
| 6 | 불편 UX | 낮음 LOW | 불편, 헷갈, 못 찾, 버튼, 글씨 |
| — | 기타 OTHER | 낮음 LOW | 아무 규칙에도 안 걸림 |

- 제목 = 제보 첫 줄, 60자에서 자름.
- 결제를 맨 위에 둔 이유: 돈이 걸린 문제는 다른 말과 섞여 있어도(「결제하다 튕겼어요」) 결제로 잡아야 한다.

### 3-2. AI 분류 (선택, 기본 꺼짐)

- 켜면 AI가 같은 7개 분류와 4단계 심각도 중에서 고르고 짧은 제목을 단다. 지시문에 「가장 높음은 결제 손실·데이터 손실에만, 높음은 크래시·플레이 불가에」를 넣어 기준을 규칙과 맞췄다.
- AI 답이 분류 목록에 없는 값이거나 형식이 깨지면 그 답을 버리고 키워드 규칙으로 내려간다.
- 근거: `classify/RuleBasedClassifier.java`, `LlmClassifier.java`, `FallbackClassifier.java`

## 4. 판단 기준

### 4-1. 같은 제보인가 (중복 묶기)

1. 본문을 정리한다: 소문자로, 링크·감탄사(ㅋㅋ, ㅠㅠ)·문장부호 제거, 띄어쓰기 하나로.
2. 같은 게임의 열린 이슈(열림·진행 중)만 비교 대상이다. 닫힌 이슈는 비교하지 않는다(E7).
3. 정리한 본문이 완전히 같으면 바로 같은 이슈.
4. 아니면 글자 두 개씩 묶은 조각이 얼마나 겹치는지(자카드 유사도) 계산해, 가장 높은 이슈가 0.55 이상이면 합친다.
5. 정리 후 남는 글자가 없으면 비교하지 않는다(E5).

예: 「5웨이브에서 게임이 튕겨요」와 「5 웨이브에서 게임이 튕겨요ㅋㅋ」 → 0.9 이상, 합침. 「루비 타워 공격력이 너무 약해요」 → 0.3 미만, 따로.

0.55는 테스트 문장들로 정한 시작값이다. 실제 제보가 모이면 잘못 묶인 사례·놓친 사례를 보고 조정한다(설정값 `DUPLICATE_THRESHOLD`).

### 4-2. 얼마나 급한가 (심각도)

- 처음 값은 분류기가 정한다.
- 같은 이슈에 더 심각한 제보가 붙으면 올리기만 하고 내리지 않는다. 한 명이라도 「튕긴다」고 하면 그 이슈는 크래시 수준으로 다룬다.
- 높음·가장 높음은 슬랙 긴급 채널, 나머지는 기본 채널로 보낸다.

### 4-3. 무엇을 보고할 것인가 (주간 보고)

- 지난 7일(월요일 0시 기준) 신규 건수 · 해결 건수 · 현재 미해결 건수
- 미해결 중 제보 수가 많은 순 상위 5건. 많이 겪은 문제가 먼저 고칠 문제라는 기준이다.
- 같은 주 보고는 서버가 여러 대여도 한 번만 나간다.
- 근거: `issue/TextNormalizer.java`, `Similarity.java`, `intake/IntakeService.java`, `report/WeeklyReportService.java`

## 5. 책임과 위임

원칙: 시스템은 받고 정리하고 제안한다. 닫는 결정은 사람이 한다. 모든 변경은 기록이 남는다.

| 주체 | 맡은 일 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|---|
| 플레이어 | 제보 작성 | 제보 채널 글, /report 명령 | 이슈 상태 변경 |
| 디스코드 봇 (연결층) | 받기와 답장 | 접수, 이슈 번호 알려 주기 | 분류·묶기 판단(처리기에 넘김) |
| 분류기 (AI·규칙) | 분류·심각도·제목 제안 | 처음 값 정하기 | 이슈 닫기, 심각도 내리기 |
| 중복 판단 (코드) | 같은 제보 묶기 | 열린 이슈에 붙이기, 심각도 올리기 | 닫힌 이슈 건드리기 |
| 알림 발송 작업 | 전달 보장 | 재시도, 실패 기록 | 내용 바꾸기 |
| 운영자 (관리자 키·관리자 슬랙 계정) | 처리 상태 결정 | 진행 중·해결·보류로 변경 | 기록 없이 바꾸기 (감사 기록 자동) |
| 오너 (작가) | 운영 정책 | 분류 키워드, 묶기 기준값, 관리자 지정, AI 사용 여부, 공개 여부 | — |

### 위임의 경계를 이렇게 그은 이유

- AI에게는 제안만 맡겼다. AI가 틀려도 비용이 작은 일(처음 분류)만 맡기고, 되돌리기 어려운 일(이슈 닫기)은 맡기지 않았다. AI가 응답하지 않아도 규칙이 대신해 흐름이 멈추지 않는다.
- 심각도는 올리기만 자동이다. 자동으로 내리면 실제로 급한 문제를 놓칠 수 있고, 자동으로 올리면 최악이라도 확인 한 번이 늘어날 뿐이다.
- 사람의 결정에는 이름이 붙는다. 상태 변경마다 누가(관리자 이름 또는 슬랙 계정)·무엇을·어떻게 바꿨는지 감사 기록에 남는다.
- 개인 정보는 받지 않는다. 작성자 디스코드 아이디는 소금 친 해시로만 저장한다. 같은 사람의 반복 제보는 알 수 있지만 누구인지는 DB에 없다.

## 6. 기술 선택 요약

| 결정 | 기각한 대안 | 이유 |
|---|---|---|
| 알림은 DB 대기열에 먼저 적고 따로 보냄 | 저장 직후 슬랙 직접 호출 | 슬랙 장애가 접수를 멈추지 않게 |
| AI 호출은 DB 작업 밖에서 | 한 작업 안에서 | 느린 외부 호출이 DB 연결을 붙잡지 않게 |
| 붙일 이슈 행을 잠금 | 충돌 나면 재시도만 | 인기 버그에 제보가 몰릴 때 재시도가 바닥났다 |
| 슬랙 서명은 받은 원래 바이트로 검사 | 스프링이 다시 조립한 본문 | 인코딩이 달라져 실제 슬랙 요청이 거절될 뻔했다 |

전체 15건은 `docs/decisions.md`, 막혔던 곳은 `docs/stuck-notes.md`.

## 7. 현재 한계

| 한계 | 영향 | 해결 방향 |
|---|---|---|
| 서버가 개인 맥에서 돈다 | 맥이 꺼져 있으면 제보를 못 받는다 (E9) | 클라우드 이전 |
| 슬랙 버튼이 동작하지 않는다 | 해결 처리를 API로 해야 한다 | 공개 주소 연결 (§8 P4) |
| 잘못 묶인 제보를 떼어낼 수 없다 | 자동 판단을 사람이 되돌릴 수단이 없다 | §8 P1 |
| 도배 방지가 없다 | 한 사람이 같은 글을 계속 올릴 수 있다 | §8 P5 |
| 이슈 조회 API에 인증이 없다 | 지금은 서버가 내 맥 안에서만 열려 있어 문제없지만, 외부에 공개하면 누구나 이슈 목록을 볼 수 있다 | 클라우드 이전 때 조회에도 관리자 키 적용 |

## 8. 개선 제안 (우선순위 순)

| # | 제안 | 무엇이 좋아지나 | 크기 |
|---|---|---|---|
| P1 | 잘못 묶인 제보 떼어내기 · 분류 고치기 + 고친 기록 남기기 | 자동 판단을 사람이 되돌릴 수 있게 된다. 사람이 고친 기록이 쌓이면 규칙·기준값을 어디서 고쳐야 하는지 데이터로 보인다 | 작음 |
| P2 | 분류 키워드를 코드 밖 설정 파일로 빼기 | 운영자가 배포 없이 「이 말은 결제 문제」를 추가할 수 있다. 판단 기준을 현업이 직접 고치게 하는 구조 | 작음 |
| P3 | 재발 표시 | 닫힌 이슈와 비슷한 새 제보에 「#1 재발 의심」을 붙여 알린다. 고친 버그가 다시 터진 걸 바로 안다 | 작음 |
| P4 | 슬랙 버튼용 공개 주소 연결 | 슬랙에서 바로 해결 처리, 시연 영상 가능 | 작음 |
| P5 | 도배 방지 (한 사람 1분 3건 등) | 공개 커뮤니티로 넓힐 때 필요 | 작음 |
| P6 | 문제 탐지 모듈 연결 (플레이 로그) | 제보하지 않은 플레이어의 이탈 구간까지 이슈로 잡힌다 | 큼 |
| P7 | 클라우드 이전 | 24시간 수집 | 중간 |
