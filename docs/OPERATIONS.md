# 운영 설계서 — 시나리오 · 분류 기준 · 판단 기준 · 책임과 위임

게임 운영 플랫폼이 플레이어 제보를 어떻게 받고, 무엇을 기준으로 나누고 묶고, 누가 어디까지 정하는지 적은 문서다. 문서의 모든 수치와 규칙은 현재 코드에 있는 값이다(근거 파일을 각 절 끝에 적었다).

---

## 1. 한 줄 요약

플레이어는 디스코드에 쓰기만 하고, 시스템은 받기·분류·묶기·알림·보고까지 자동으로 처리하며, 이슈를 닫는 결정은 사람만 한다.

```
플레이어 ──글──▶ 디스코드 봇 ──▶ 분류(AI 또는 규칙) ──▶ 중복 판단 ──▶ 이슈 DB
                    │                                              │
                    └──── 접수 답장(이슈 번호) ◀───────────────────┘
                                                                   │
                                          알림 대기열 ──▶ 슬랙(개발팀)
                                                                   │
                                         운영자 ──상태 변경──▶ 이슈 DB + 감사 기록
                                           │
                                           └─떼어내기·분류 고치기──▶ 고친 기록 ──▶ 키워드 파일·기준값 조정
```

자동 판단이 틀리면 사람이 되돌리고, 되돌린 기록이 다시 판단 기준을 고치는 근거가 된다(§5-2).

## 2. 예상 시나리오

### 2-1. 정상 흐름

| # | 상황 | 시스템 반응 | 플레이어가 보는 것 | 개발팀이 보는 것 |
|---|---|---|---|---|
| S1 | 처음 보는 버그 제보 「보스 웨이브에서 게임이 튕겨요」 | 크래시·높음으로 분류, 이슈 #1 생성, 알림 대기열에 기록 | 「접수했어요. 이슈 #1 로 개발팀에 전달합니다.」 | 긴급 채널에 「새 이슈 #1 · CRASH/HIGH · 제보 1건」 |
| S2 | 같은 버그를 다른 말로 「보스웨이브에서 튕김ㅠㅠ」 | 열린 이슈 #1과 비슷하다고 판단해 합침, 제보 수 +1 | 「비슷한 제보가 있어 이슈 #1 에 합쳤어요. 같은 제보 2건째입니다.」 | 새 알림 없음(같은 이슈 반복 알림 방지) |
| S3 | 다른 내용 「젤리 색깔이 비슷해서 헷갈려요」 | 불편·낮음으로 분류, 이슈 #2 생성 | 「접수했어요. 이슈 #2 …」 | 기본 채널에 새 이슈 알림 |
| S4 | 이미 있는 이슈에 더 심각한 제보가 붙음 (버그로 접수된 이슈에 「…하다가 튕겨요」) | 이슈 심각도를 올림 | 합쳤다는 답장 | 「심각도 상승」 알림 |
| S5 | 결제 문제 「결제했는데 보석이 안 들어왔어요」 | 결제·가장 높음으로 분류 | 접수 답장 | 긴급 채널에 즉시 알림 |
| S6 | 월요일 오전 9시 | 게임별 주간 보고 생성 | — | 신규·해결·미해결 건수와 제보 많은 미해결 상위 5건 |
| S7 | 운영자가 이슈를 해결 처리 | 상태 변경 + 누가 언제 바꿨는지 기록 | — | 슬랙 알림의 버튼(관리자 슬랙 계정만) 또는 API |
| S8 | 「스테이지 3에서 게임이 튕겨요」와 「스테이지 3에서 게임이 느려요」가 한 이슈로 묶임 (글자 겹침 0.6. 2026-10-20 P9 이후로는 분류가 달라 묶이지 않는다 — 같은 분류 안에서 잘못 묶이면 같은 방법으로 떼어낸다) | 운영자가 「느려요」 제보를 떼어내면 그 글만 다시 분류해 성능·중간 새 이슈로 만든다 | — | 「새 이슈(#1에서 떼어냄)」 알림. 고친 기록에 묶일 때 유사도 0.6이 남는다 |
| S9 | 「버튼 색이 이상해요」(디자인 의견)가 버그·중간으로 잡힘 | 운영자가 불편·낮음으로 고침. 사람은 심각도를 내릴 수 있다 | — | 고친 기록 요약에 「버그→불편」이 쌓인다. (v1 규칙에서는 「결제 화면 글씨가 작아요」가 결제로 잡혔고, v2 에서 고쳤다 — §3-3) |
| S10 | 운영자가 「사라지」를 버그 키워드로 추가 | `config/classifier-rules.json` 을 저장하면 다음 제보부터 반영(재시작 없음) | — | — |
| S11 | 같은 날 #젤리패닉-버그제보 와 #보석타워-버그제보 에 똑같이 「로딩에서 멈춰요」 | 채널로 게임을 정해 게임별로 따로 이슈를 만든다(게임이 다르면 묶지 않음) | — | 각 게임 슬랙 채널로 따로 알림, 주간 보고도 게임마다 |
| S12 | 새 게임 무브퓨 출시 | `config/games.json` 에 한 줄 추가 → 디스코드 #무브퓨-버그제보 · 슬랙 #무브퓨-알림 만들기 → 서버 재시작 | — | 코드·DB 작업 없이 게임이 늘어난다 |

### 2-2. 예외·장애 흐름

| # | 상황 | 시스템 반응 | 왜 이렇게 했나 |
|---|---|---|---|
| E1 | 디스코드가 같은 메시지를 두 번 보냄 | 제보는 1건만 저장, 「이미 접수된 제보예요」 | 채널+메시지 번호 고유 제약. 서버를 여러 대 띄워도 지켜진다 |
| E2 | 같은 버그 제보 8건이 동시에 들어옴 | 이슈 1개, 제보 8건으로 정확히 묶임 | 붙일 이슈 행을 잠가 차례로 처리 (실제로 막혔던 문제, stuck-notes 1·2) |
| E3 | 슬랙이 죽어 있음 | 제보·이슈는 정상 저장. 알림은 2초·4초·8초·16초 간격으로 다시 보내고 5번 실패하면 실패로 표시해 남김 | 외부 서비스 장애가 접수를 멈추게 하지 않는다 |
| E4 | AI 분류가 응답이 없거나 엉뚱한 형식으로 답함 | 키워드 규칙으로 분류해 계속 진행 | 분류 정확도보다 접수가 끊기지 않는 쪽이 먼저 |
| E5 | 링크·이모지만 있는 글 (「ㅋㅋㅋ」, 스크린샷 주소만) | 비교하지 않고 따로 이슈 생성 | 빈 글끼리 묶이면 무관한 제보가 한 이슈로 몰린다 (독립 검토에서 발견) |
| E6 | 봇이 쓴 글 · 제보 채널이 아닌 곳의 글 | 무시 | 봇끼리 대화 고리, 잡담 수집 방지 |
| E7 | 이미 해결된 버그가 다시 제보됨 | 새 이슈로 생성하고 「재발 의심(최근 해결한 #1과 비슷)」을 알림·디스코드 답장에 적는다 | 고친 뒤 다시 생긴 건 원인이 다를 수 있어 새 사건으로 본다. 다만 고친 버그가 다시 터진 사실은 바로 보여야 한다(§4-4) |
| E8 | 닫힌 이슈를 다시 열려는데 같은 내용의 열린 이슈가 이미 있음 | 409(충돌)로 거절, 새로고침 안내 | 같은 내용의 열린 이슈가 둘이 되는 것을 막는다 |
| E9 | 서버가 꺼져 있던 동안 올라온 글 | 수집하지 않음 | 현재 한계. 24시간 운영은 클라우드 이전 필요 |
| E10 | 슬랙 버튼 요청이 위조됐거나 5분이 지남 | 401로 거절, 상태 변경 없음 | 서명 확인 없이는 누구나 상태 변경 요청을 만들 수 있다 |
| E11 | 운영자가 키워드 파일을 잘못 고침 (없는 분류 이름, 빈 키워드, JSON 깨짐), 또는 형식은 맞지만 평가 관문 미달(회귀 문장이 다시 틀림 · dev 정확도 95% 미만) | 그 파일을 받지 않고 직전 규칙으로 계속 분류. 오류 내용(미달이면 틀린 문장까지)은 서버 기록과 규칙 조회 API에 보인다 | 오타 하나로 분류가 멈추면 안 된다. 깃 관문 테스트를 거치지 않는 운영 중 저장도 같은 기준을 지나야 한다(P11) |
| E12 | 인터넷에서 공개 주소로 슬랙 버튼 외 주소(이슈 목록 등)를 요청 | 404 | 바깥에 여는 문은 슬랙 버튼 주소 하나뿐이다(§6) |
| E13 | 제보가 하나뿐인 이슈, 닫힌 이슈에서 떼어내기 | 409로 거절 | 떼어내면 빈 이슈가 남는다(이 경우는 분류 고치기). 닫힌 이슈는 다시 연 뒤에 |
| E14 | 사람이 「낮음」으로 내린 이슈에 「튕겨요」 제보가 붙음 | 제보 수만 늘고 심각도는 그대로 | 사람 판단을 자동이 덮지 않는다(§4-2) |
| E15 | 게임 슬랙 채널을 아직 안 만들었거나 이름이 틀림 | 공용 채널로 한 번 돌려 보내고 「게임 채널로 못 보내 여기로 왔어요」를 붙인다 | 다시 보내도 안 되는 오류라 재시도만 하면 알림이 통째로 사라진다 |
| E16 | 게임 목록에서 한 채널을 두 게임에 걸거나 코드를 겹쳐 씀 | 서버가 켜지지 않고 무엇이 틀렸는지 기록에 남긴다 | 엉뚱한 게임으로 제보가 쌓이면 나중에 가려내기 어렵다. 분류 키워드(E11)와 달리 틀리면 멈추는 쪽을 골랐다 |
| E17 | 게임 채널 안 스레드·포럼 글 | 부모 채널로 게임을 정한다 | 스레드 ID 로 찾으면 제보가 무시되거나 기본 게임으로 잘못 들어간다(독립 검토에서 발견) |
| E18 | 터널이 저절로 다시 켜져 슬랙 버튼 주소가 바뀜(맥 재시동·OrbStack 재시작) | 서버가 1분마다 터널에 지금 주소를 묻고, 바뀌면 공용 긴급 채널에 새 주소와 넣을 곳을 한 번 알린다 | 버튼이 조용히 안 먹는 상태를 사람이 모르고 지나가게 두지 않는다. 같은 주소는 대기열 중복 방지 키로 한 번만 |

## 3. 분류 기준

분류기는 제보 하나에 분류 · 심각도 · 제목을 붙인다.

### 3-1. 키워드 규칙 (기본값, 외부 호출 없음)

규칙은 코드가 아니라 `config/classifier-rules.json` 에 있다. 운영자가 이 파일을 고치고 저장하면 다음 제보부터 반영된다. 이미 분류된 이슈는 바뀌지 않는다. 위에서부터 먼저 걸리는 규칙 하나를 쓴다. 더 심각한 규칙을 위에 두었다.

| 순서 | 분류 | 심각도 | 걸리는 말 (일부) |
|---|---|---|---|
| 1 | 결제 PAYMENT | 가장 높음 CRITICAL | 돈이 오간 표현: 결제했, 두 번 결제, 결제 오류, 결제가 안, 결제하다, 환불해, 환불 요청, 구매했는데, 충전했는데, 영수증 |
| 2 | 버그 BUG | 중간 MEDIUM | 게임 안 충전: 하트 충전, 에너지 충전 |
| 3 | 불편 UX | 낮음 LOW | 화면 글씨, 글씨가 작, 글자 크기 |
| 4 | 기타 OTHER | 낮음 LOW | 문의: 어떻게 되나요, 어디서 하나요, 궁금, 가격, 비싸 |
| 5 | 결제 PAYMENT | 가장 높음 CRITICAL | 결제, 환불, 충전, 결제창 |
| 6 | 크래시 CRASH | 높음 HIGH | 튕, 크래시, 강제 종료, 멈춤, 먹통, 접속 불가, 꺼져, 검은 화면 |
| 7 | 버그(진행 손실) BUG | 높음 HIGH | 날아갔, 초기화, 처음부터 다시, 진행 불가, 저장이 안 |
| 8 | 성능 PERFORMANCE | 중간 MEDIUM | 렉, 느려, 프레임, 버벅, 로딩이 길, 배터리, 발열 |
| 9 | 버그 BUG | 중간 MEDIUM | 버그, 오류, 안 돼, 이상해, 사라져, 끼어, 반응이 없, 안 눌려, 못 받 |
| 10 | 밸런스 BALANCE | 낮음 LOW | 밸런스, 너무 세, 너무 약, 너프, 어려워, 난이도, 확률 |
| 11 | 불편 UX | 낮음 LOW | 불편, 헷갈, 못 찾, 버튼, 글씨, 옵션, 조작감 |
| — | 기타 OTHER | 낮음 LOW | 아무 규칙에도 안 걸림 |

- 제목 = 제보 첫 줄, 60자에서 자름.
- 결제를 맨 위에 둔 이유: 돈이 걸린 문제는 다른 말과 섞여 있어도(「결제하다 튕겼어요」) 결제로 잡아야 한다. v1 은 「결제」「충전」 낱말만 보고 잡아서 「결제 화면 글씨가 작아요」「하트 충전이 안 돼요」까지 결제·가장 높음으로 올렸다. v2 는 돈이 오간 표현으로 좁혔다가 「결제가 두 번 됐어요」 같은 흔한 결제 문장을 놓쳤다. v3 는 2~4번 규칙으로 돈 문제가 아닌 경우를 먼저 걸러 내고 5번에서 넓게 잡는다(§3-3, 막힌 곳 10).
- 파일 검사: 분류·심각도 이름이 목록에 없거나, 키워드가 비어 있거나, 형식이 깨지면 파일 전체를 받지 않는다(E11). 적용 중인 규칙과 마지막 오류는 `GET /api/admin/classifier/rules` 로 본다.

### 3-2. AI 분류 (선택, 기본 꺼짐)

- 켜면 AI가 같은 7개 분류와 4단계 심각도 중에서 고르고 짧은 제목을 단다. 지시문에 「가장 높음은 결제 손실·데이터 손실에만, 높음은 크래시·플레이 불가에」를 넣어 기준을 규칙과 맞췄다.
- AI 답이 분류 목록에 없는 값이거나 형식이 깨지면 그 답을 버리고 키워드 규칙으로 내려간다.
- 근거: `config/classifier-rules.json`, `classify/RuleBasedClassifier.java`, `FileRuleSource.java`, `LlmClassifier.java`, `FallbackClassifier.java`

### 3-3. 규칙을 숫자로 고친다 (평가 하네스)

규칙은 감으로 고치지 않는다. 정답을 붙인 제보 90건(규칙을 고칠 때 보는 dev 60 · 보지 않는 holdout 30)으로 전후를 잰다. 자세한 것은 [`docs/EVAL.md`](EVAL.md).

| 규칙 | 분류 정확도 dev | 회귀 16문장 | holdout |
|---|---|---|---|
| v1 (처음) | 65.0% | 15/16 | 50.0% |
| v2 (dev 틀린 사례만 보고 고침) | 98.3% | 1/16 | 83.3% |
| v3 (독립 검토 반영) | 100% | 16/16 | 83.3% |

v2 는 dev 점수를 올리느라 흔한 결제 문장을 놓쳤다(막힌 곳 10). 그래서 점수와 별도로 「한 번 틀렸던 문장」을 회귀 묶음으로 고정한다. 정확도가 바닥값(dev 95%, holdout 80%) 밑이거나 회귀 문장이 하나라도 틀리면 테스트가 막는다(`EvalGateTest`). 서버가 실행 중에 다시 읽는 규칙 파일도 같은 기준(dev 95% · 회귀 전부)을 지나야 받는다(`EvalRuleGate`, E11). holdout 은 이 관문에 넣지 않는다(규칙 고치기 고리에 시험지가 새지 않게).

## 4. 판단 기준

### 4-1. 같은 제보인가 (중복 묶기)

1. 본문을 정리한다: 소문자로, 링크·감탄사(ㅋㅋ, ㅠㅠ)·문장부호 제거, 띄어쓰기 하나로.
2. 같은 게임의 열린 이슈(열림·진행 중)만 비교 대상이다. 닫힌 이슈는 비교하지 않는다(E7).
3. 정리한 본문이 완전히 같으면 바로 같은 이슈.
4. 아니면 **분류가 같은 이슈만** 남긴다. 이슈의 지금 분류(사람이 고친 값) 또는 처음 자동 분류 중 하나가 새 글의 분류와 같으면 비교 대상이다.
5. 글자 두 개씩 묶은 조각이 얼마나 겹치는지(자카드 유사도) 계산해, 가장 높은 이슈가 0.20 이상이면 합친다.
6. 정리 후 남는 글자가 없으면 비교하지 않는다(E5).

예: 「로그인하면 바로 튕겨요」와 「로그인 후 바로 튕김」 → 둘 다 크래시, 0.33, 합침. 「스테이지 3에서 게임이 튕겨요」와 「…느려요」 → 글자는 0.6 겹치지만 크래시와 성능이라 따로.

**왜 분류를 먼저 보나 (P9, 2026-10-20 작가 결정).** 처음엔 글자만 보고 0.55 로 묶었는데, 평가해 보니 같은 문제 20쌍 중 1쌍만 묶였다. 기준을 낮추면 「튕겨요/느려요」처럼 글자는 겹치는데 증상이 다른 글이 묶였다. 분류가 같을 때만 비교하면 이런 쌍이 빠져서 기준을 0.20 까지 내려도 다른 문제를 묶은 건 0건이고, 같은 문제는 20쌍 중 8쌍을 묶는다(docs/EVAL.md §3). 다른 문제를 묶은 쌍이 처음 나오는 0.10 에서 한 칸 위를 골랐다(0.15 면 10쌍이지만 여유가 없다). 평가 쌍이 40개뿐이고 같은 사람이 써서 실제로는 이보다 낮을 수 있다 → 실제 제보 20건이 쌓이면 다시 잰다. 잘못 묶여도 떼어내기(§4-5)로 되돌릴 수 있다.

처음 자동 분류를 같이 보는 이유: 사람이 「결제→불편」으로 고쳐도 같은 글은 자동으로 다시 「결제」가 나온다. 지금 분류만 보면 고친 이슈에 비슷한 제보가 안 붙고 같은 문제의 새 이슈가 계속 생긴다(시험에서 발견).

되돌리기: `DUPLICATE_SAME_CATEGORY_ONLY=false`, `DUPLICATE_THRESHOLD=0.55` 후 서버 다시 켜기.

### 4-2. 얼마나 급한가 (심각도)

- 처음 값은 분류기가 정한다.
- 같은 이슈에 더 심각한 제보가 붙으면 올리기만 하고 내리지 않는다(같은 분류 안에서. 예: 버그 이슈에 「진행 불가」가 붙으면 높음). 버그 이슈에 「튕긴다」는 글이 오면 분류가 크래시라 붙지 않고 크래시 새 이슈가 되며, 높음이라 긴급 채널로 바로 간다.
- 사람이 분류를 고친 이슈는 자동으로 올리지 않는다. 제보 수만 늘고, 다시 올릴지는 사람이 정한다.
- 높음·가장 높음은 슬랙 긴급 채널, 나머지는 기본 채널로 보낸다.

### 4-3. 무엇을 보고할 것인가 (주간 보고)

- 지난 7일(월요일 0시 기준) 신규 건수 · 해결 건수 · 현재 미해결 건수
- 미해결 중 제보 수가 많은 순 상위 5건. 많이 겪은 문제가 먼저 고칠 문제라는 기준이다.
- 같은 주 보고는 서버가 여러 대여도 한 번만 나간다.
### 4-4. 다시 생긴 문제인가 (재발)

- 새 이슈가 생길 때만 본다. 열린 이슈에 붙는 제보는 재발이 아니다.
- 지난 30일 안에 「해결」로 닫은 이슈와 비교한다. 「고치지 않기로 함」은 고친 적이 없으니 재발로 보지 않는다.
- 묶기와 같은 기준(분류가 같을 때만, 0.20)을 쓴다. 넘으면 가장 비슷한 이슈 번호와 유사도를 새 이슈에 적는다. 닫힌 이슈를 다시 열지는 않는다.
- 설정값 `RECURRENCE_WINDOW_DAYS`(기본 30).

### 4-5. 사람이 고칠 때

- 떼어내기: 고른 제보 하나를 원래 이슈에서 빼 새 이슈로 만든다. 새 이슈의 분류는 그 제보 글만 보고 다시 정한다. 원래 이슈의 심각도는 자동으로 내리지 않는다(떼어낸 제보 때문에 올라간 것이라도, 내릴지는 사람이 분류 고치기로 정한다).
- 대표 제보를 떼어내면 남은 제보 중 가장 먼저 묶인 것이 대표가 되고 제목도 바뀐다. 이후 중복 비교는 새 대표 글로 한다. 그래야 잘못 묶인 글이 계속 남의 제보를 끌어오지 않는다(S8 테스트로 확인).
- 분류 고치기: 분류·심각도 중 하나만 바꿔도 된다. 사람은 심각도를 내릴 수 있다. 사람이 올리면 긴급 알림이 다시 나간다(열린 이슈만).
- 슬랙에서 바로: 카드의 「분류 고치기」「잘못 묶임 떼어내기」 버튼이 입력 창을 연다. 저장하면 API 와 같은 처리(고친 기록·감사 기록 `slack:<멤버 ID>`)를 하고 원래 카드를 그 자리에서 바꾼다. 관리자 슬랙 ID 가 아니면 창에 오류를 띄우고 바꾸지 않는다. 닫힌 이슈는 다시 연 뒤에 고친다.
- 닫힌 이슈: 떼어내기는 막는다(다시 연 뒤에). 분류 고치기는 기록 정리용으로 허용하고 알림은 보내지 않는다.
- 근거: `issue/TextNormalizer.java`, `Similarity.java`, `intake/IntakeService.java`, `correction/CorrectionService.java`, `report/WeeklyReportService.java`

원칙: 시스템은 받고 정리하고 제안한다. 닫는 결정은 사람이 한다. 모든 변경은 기록이 남는다.

| 주체 | 맡은 일 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|---|
| 플레이어 | 제보 작성, 재현 정보 | 제보 채널 글, /report 명령(버전·기기·재현 순서·스크린샷), 답글로 재현 정보 더하기 | 이슈 상태 변경 |
| 디스코드 봇 (연결층) | 받기와 답장 | 접수, 이슈 번호 알려 주기 | 분류·묶기 판단(처리기에 넘김) |
| 분류기 (AI·규칙) | 분류·심각도·제목 제안 | 처음 값 정하기 | 이슈 닫기, 심각도 내리기, 사람이 고친 값 되돌리기 |
| 중복 판단 (코드) | 같은 제보 묶기 | 열린 이슈에 붙이기, 심각도 올리기 | 닫힌 이슈 건드리기 |
| 알림 발송 작업 | 전달 보장 | 재시도, 실패 기록 | 내용 바꾸기 |
| 운영자 (관리자 키·관리자 슬랙 계정) | 처리 상태 결정, 자동 판단 바로잡기 | 진행 중·해결·보류로 변경, 잘못 묶인 제보 떼어내기, 분류·심각도 고치기(내리기 포함), 개발 AI·Jira 로 넘기기 | 기록 없이 바꾸기 (감사 기록·고친 기록 자동) |
| 개발자·개발 AI | 고치기 | 지시서·Jira 티켓 받아 재현·수정, PR 에 ops-번호 | 운영 이슈 상태 바꾸기(PR 을 사람이 합칠 때 서버가 바꾼다) |
| QA (관리자 슬랙 계정 · Jira) | 고친 것 확인 | 「QA 확인 완료」·「아직 나요」, Jira 티켓 완료 | 확인 없이 플레이어에게 「고쳤어요」 보내기 |
| 오너 (작가) | 운영 정책 | 분류 키워드 파일, 묶기 기준값, 재발 기간, 관리자 지정, AI 사용 여부, 공개 여부 | — |

### 위임의 경계를 이렇게 그은 이유

- AI에게는 제안만 맡겼다. AI가 틀려도 비용이 작은 일(처음 분류)만 맡기고, 되돌리기 어려운 일(이슈 닫기)은 맡기지 않았다. AI가 응답하지 않아도 규칙이 대신해 흐름이 멈추지 않는다.
- 심각도는 올리기만 자동이다. 자동으로 내리면 실제로 급한 문제를 놓칠 수 있고, 자동으로 올리면 최악이라도 확인 한 번이 늘어날 뿐이다.
- 사람의 결정에는 이름이 붙는다. 상태 변경마다 누가(관리자 이름 또는 슬랙 계정)·무엇을·어떻게 바꿨는지 감사 기록에 남는다.
- 사람이 고친 값은 사람 것이다. 분류를 고치면 「누가 판단했나」가 human 으로 바뀐다. 이후 자동으로 바뀌는 건 심각도 올리기 하나뿐이다.
- 개인 정보는 받지 않는다. 작성자 디스코드 아이디는 소금 친 해시로만 저장한다. 같은 사람의 반복 제보는 알 수 있지만 누구인지는 DB에 없다.

### 5-2. 사람이 고친 기록이 기준을 고치는 고리

자동 판단을 되돌릴 때마다 「고친 기록」이 한 줄씩 쌓인다(무엇을 · 어떻게 · 고치기 전엔 누가 판단했나 · 묶일 때 유사도 · 이유). `GET /api/corrections/summary` 가 이를 묶어 보여 준다.

| 요약 항목 | 읽는 법 | 고칠 곳 |
|---|---|---|
| 분류가 자주 바뀐 방향 (예: 결제→불편 5건) | 같은 방향이 쌓이면 그 키워드가 너무 넓다 | `config/classifier-rules.json` |
| 떼어낸 제보들의 묶일 때 유사도 (최소·평균·최대) | 대부분 기준값(0.20) 바로 위라면 기준값이 낮다 | `DUPLICATE_THRESHOLD` |
| 심각도를 내린 횟수 | 많으면 자동 판단이 과하게 잡는다 | 키워드 순서·심각도 |
| 틀린 판단 출처 (rules / llm / similarity) | AI를 켰을 때 규칙보다 나은지 | AI 사용 여부 |

판단 기준을 감으로 바꾸지 않고, 사람이 바로잡은 횟수로 바꾼다.

## 6. 기술 선택 요약

| 결정 | 기각한 대안 | 이유 |
|---|---|---|
| 알림은 DB 대기열에 먼저 적고 따로 보냄 | 저장 직후 슬랙 직접 호출 | 슬랙 장애가 접수를 멈추지 않게 |
| AI 호출은 DB 작업 밖에서 | 한 작업 안에서 | 느린 외부 호출이 DB 연결을 붙잡지 않게 |
| 붙일 이슈 행을 잠금 | 충돌 나면 재시도만 | 인기 버그에 제보가 몰릴 때 재시도가 바닥났다 |
| 슬랙 서명은 받은 원래 바이트로 검사 | 스프링이 다시 조립한 본문 | 인코딩이 달라져 실제 슬랙 요청이 거절될 뻔했다 |
| 키워드는 파일, 저장하면 다음 제보부터 | 코드에 고정 / DB 관리 화면 | 운영자가 배포 없이 고치고, 깃으로 바뀐 내역이 남는다. 틀린 파일은 받지 않는다 |
| 슬랙 버튼은 「문 하나만 여는」 중계(nginx) 뒤에 임시 공개 주소(cloudflared) | 서버 전체 공개 / 포트 열기 | 인터넷에는 `/slack/interactions` POST 하나만 보이고 나머지는 404. 서버 포트 8080은 내 컴퓨터 안에서만 열린다. 계정·도메인 없이 바로 시연 가능 |
| 떼어낸 이슈는 글이 같아도 따로 둔다 | 자동으로 다시 합침 | 사람이 일부러 나눈 걸 시스템이 되돌리면 안 된다 |

전체 15건은 `docs/decisions.md`, 막혔던 곳은 `docs/stuck-notes.md`.
