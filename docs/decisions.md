# 설계 결정

| # | 결정 | 기각한 대안 | 이유 |
|---|---|---|---|
| 1 | 슬랙 알림은 DB 대기열(outbox)에 먼저 적고 별도 작업이 보낸다 | 제보 저장 직후 슬랙 직접 호출 | 슬랙이 느리거나 죽어도 제보 접수가 멈추지 않고, 보내지 못한 알림이 DB에 남아 다시 보낼 수 있다 |
| 2 | 분류(LLM 호출)는 DB 트랜잭션 밖에서 한다 | 트랜잭션 안에서 분류 | 외부 호출을 기다리는 동안 DB 연결과 잠금을 붙잡지 않는다 |
| 3 | LLM 실패·형식 오류 시 키워드 규칙 분류로 내려간다 | LLM만 사용, 실패 시 접수 거절 | 분류 품질보다 접수가 끊기지 않는 쪽이 운영에서 중요하다 |
| 4 | 중복 판단은 글자 2개 묶음 자카드 유사도 | 형태소 분석기 · 임베딩 | 의존성 없이 한국어 띄어쓰기 차이에 강하다. 임베딩으로 바꿀 때는 유사도를 계산하는 한 곳(`IntakeService` 의 비교 반복문)을 바꾸면 된다. 분류기와 달리 아직 인터페이스로 빼지는 않았다 |
| 5 | 열린 이슈에 「같은 정규화 본문 키」 부분 고유 인덱스 | 애플리케이션 잠금만 | 동시에 똑같은 제보가 들어올 때 이슈가 두 개 생기는 것을 DB가 마지막으로 막는다. 충돌 나면 재시도해서 기존 이슈에 붙인다 |
| 6 | 기존 이슈에 붙일 때는 그 이슈 행을 비관적 잠금(SELECT … FOR UPDATE) | 낙관적 잠금 + 재시도만 | 인기 버그는 제보가 몰린다. 낙관적 잠금만 쓰면 8건 동시 접수에서 재시도가 바닥났다(`stuck-notes.md` 1) |
| 7 | 같은 디스코드 메시지 재수신은 `(채널, 외부 ID)` 고유 제약으로 1건만 저장 | 메모리 캐시로 중복 거르기 | 서버를 여러 대 띄우거나 재시작해도 지켜진다 |
| 8 | 알림 대기열은 `FOR UPDATE SKIP LOCKED` 로 집는다 | 단일 서버 가정 | 서버가 여러 대여도 같은 알림을 동시에 집지 않는다. 다만 슬랙 전송 뒤 DB 반영 전에 서버가 죽으면 다시 보내므로 「최소 한 번 전달」이다. 정확히 한 번은 슬랙 쪽 중복 제거 수단이 없어 포기했다 |
| 9 | 작성자 ID는 소금 친 SHA-256 해시로만 저장 | 원본 ID 저장 | 같은 사람의 반복 제보는 알 수 있으면서 개인 식별 정보를 DB에 남기지 않는다 |
| 10 | 슬랙 버튼 요청은 서명(HMAC)과 5분 시각 제한을 확인한 뒤, 관리자 슬랙 ID 목록에 있을 때만 상태 변경 | 버튼 값만 믿고 처리 | 서명이 없으면 누구나 상태를 바꾸는 요청을 위조할 수 있다 |
| 11 | 디스코드 라이브러리 이벤트는 얇은 연결층에서 `DiscordInbound` 로 바꿔 처리기로 넘긴다 | 리스너 안에 접수 로직 | 실제 디스코드 없이 처리 로직을 전부 테스트할 수 있다 |
| 12 | 관리자 API 키는 상수 시간 비교, 빈 키는 무시 | 문자열 equals | 응답 시간 차이로 키를 추측하는 공격을 막고, 설정이 비어 있을 때 아무나 통과하는 사고를 막는다 |
| 13 | 슬랙 서명은 요청 본문의 원래 바이트로 계산한다 | `@RequestBody String` | 스프링이 폼 본문을 다시 조립하면 인코딩이 바뀌어 실제 슬랙 요청의 서명이 어긋난다(독립 검토에서 발견) |
| 14 | 정규화 후 글자가 남지 않는 제보(링크·이모지만)는 비교하지 않고 따로 이슈를 만든다 | 빈 글끼리 같은 이슈 | 무관한 스크린샷 링크들이 한 이슈로 몰렸다(독립 검토에서 발견) |
| 15 | 주간 보고는 「게임+주」 키로 한 번만 대기열에 넣는다 | 예약 작업 잠금 라이브러리 | 서버 여러 대에서 같은 예약 작업이 돌아도 보고는 하나. DB 고유 인덱스 하나로 해결된다 |
| 16 | 분류 키워드는 `config/classifier-rules.json`, 바뀐 시각을 보고 다음 제보부터 다시 읽는다 | 코드 고정 / DB와 관리 화면 / 파일 감시 스레드 | 운영자가 배포 없이 고치고 깃에 바뀐 내역이 남는다. 제보마다 파일 시각만 확인하므로 감시 스레드가 필요 없다. 틀린 파일은 통째로 거절하고 직전 규칙을 유지한다 |
| 17 | 떼어낸 제보는 그 글만으로 다시 분류해 새 이슈를 만들고, 원래 이슈의 심각도는 내리지 않는다 | 원래 분류 복사 / 심각도 자동 재계산 | 잘못 묶인 글은 원래 분류도 틀렸을 가능성이 높다. 심각도를 자동으로 내리는 길은 하나도 두지 않는다는 원칙(§4-2)을 지킨다 |
| 18 | 재발은 「최근 30일 안에 해결로 닫은 이슈」만, 새 이슈에 표시만 하고 다시 열지 않는다 | 닫힌 이슈 자동 재오픈 | 고친 뒤 다시 생긴 문제는 원인이 다를 수 있다. 자동 재오픈은 해결 기록을 지운다. 「고치지 않기로 함」은 고친 적이 없으니 제외 |
| 19 | 슬랙 버튼 공개는 nginx 로 `/slack/interactions` POST 하나만 넘기고 cloudflared 임시 주소로 연결 | 서버 전체 공개 / ngrok(계정 필요) / 공유기 포트 열기 | 조회 API에 인증이 없는 지금 구조에서도 바깥에 보이는 건 서명 검사하는 주소 하나뿐이다. 계정·도메인 없이 시연할 수 있다. 대신 주소가 켤 때마다 바뀐다 |
| 20 | 게임은 `config/games.json` 한 파일로 정하고, 디스코드는 채널(ID 또는 이름)로 게임을 고른다. 슬랙은 게임 채널 → 공용 채널 | 게임마다 봇·서버를 따로 / 글 앞에 [게임] 태그를 쓰게 함 / DB와 관리 화면 | 플레이어는 게임 채널에 쓰기만 하면 되고(태그 실수 없음), 게임 추가가 파일 한 줄이다. 이름 매칭은 설정이 쉽지만 채널 이름을 바꾸면 끊기므로 운영에서는 ID 를 권장. 틀린 목록은 켜지 않는다(키워드 파일과 반대 — 잘못 쌓인 제보는 되돌리기 어렵다) |
| 21 | AI 에이전트는 REST API 위의 얇은 MCP 서버로 붙이고, 전용 키(`AGENT_API_KEY` → 감사 기록 `ai-agent`)를 준다. 바꾸는 도구 3개는 이유 필수·확인 필요 표시. 에이전트 키로는 해결·보류를 서버가 403 으로 막고, 플레이어 글은 `<player_report>` 로 감싸 믿지 않는 데이터로 넘긴다 | 서버 안에 MCP 를 넣기 / 사람 키 같이 쓰기 / 에이전트가 해결까지 | 서버는 그대로 두고 어떤 에이전트든 붙일 수 있다. 키를 나누면 사람과 에이전트가 한 일을 기록만 보고 가르고, 에이전트만 즉시 끊을 수 있다. 고쳤는지는 개발팀만 안다 |
| 22 | 분류 규칙은 정답 붙인 90건(dev 60 · holdout 30)과 회귀 문장으로 전후를 재고, 바닥값 밑이거나 회귀가 틀리면 테스트가 막는다. 규칙은 dev 틀린 사례만 보고 고치고, holdout 은 평소 숨긴다 | 감으로 고치기 / 점수만 보기 | 점수만 보면 v2 처럼 묶음 밖의 비싼 오류(결제 누락)를 늘린다. 틀렸을 때 비용이 큰 분류는 회귀 문장으로 따로 지킨다. v1→v3: dev 65→100%, holdout 50→83%, 결제 회귀 16/16 |
| 23 | 맥에서 컨테이너를 돌리는 도구를 Docker Desktop 에서 OrbStack 으로 바꾼다. 서비스에 `restart: unless-stopped` 를 붙이고, `start.sh` 의 Docker 확인에 20초 제한을 둔다 | Docker Desktop 그대로(자원만 줄이기) / 맥에 자바·PostgreSQL 직접 설치 / 클라우드 이전 | 맥북 한 대로 돌리는 작업이 많아 메모리 부담이 컸다. 2026-10-20 에는 맥 CPU 가 사실상 100% 인 상태에서 Docker Desktop 본체가 오전부터 응답을 멈췄고(내부 기록 `/time … deadline exceeded` 167번), 오후에 디스코드 봇 연결이 끊겨 두 시간가량 제보를 못 받았다.
