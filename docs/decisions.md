# 설계 결정

| # | 결정 | 기각한 대안 | 이유 |
|---|---|---|---|
| 1 | 슬랙 알림은 DB 대기열(outbox)에 먼저 적고 별도 작업이 보낸다 | 제보 저장 직후 슬랙 직접 호출 | 슬랙이 느리거나 죽어도 제보 접수가 멈추지 않고, 보내지 못한 알림이 DB에 남아 다시 보낼 수 있다 |
| 2 | 분류(LLM 호출)는 DB 트랜잭션 밖에서 한다 | 트랜잭션 안에서 분류 | 외부 호출을 기다리는 동안 DB 연결과 잠금을 붙잡지 않는다 |
| 3 | LLM 실패·형식 오류 시 키워드 규칙 분류로 내려간다 | LLM만 사용, 실패 시 접수 거절 | 분류 품질보다 접수가 끊기지 않는 쪽이 운영에서 중요하다 |
| 4 | 중복 판단은 글자 2개 묶음 자카드 유사도 | 형태소 분석기 · 임베딩 | 의존성 없이 한국어 띄어쓰기 차이에 강하다. 임베딩은 분류기처럼 인터페이스로 갈아끼울 자리만 둔다 |
| 5 | 열린 이슈에 「같은 정규화 본문 키」 부분 고유 인덱스 | 애플리케이션 잠금만 | 동시에 똑같은 제보가 들어올 때 이슈가 두 개 생기는 것을 DB가 마지막으로 막는다. 충돌 나면 재시도해서 기존 이슈에 붙인다 |
| 6 | 기존 이슈에 붙일 때는 그 이슈 행을 비관적 잠금(SELECT … FOR UPDATE) | 낙관적 잠금 + 재시도만 | 인기 버그는 제보가 몰린다. 낙관적 잠금만 쓰면 8건 동시 접수에서 재시도가 바닥났다(`stuck-notes.md` 1) |
| 7 | 같은 디스코드 메시지 재수신은 `(채널, 외부 ID)` 고유 제약으로 1건만 저장 | 메모리 캐시로 중복 거르기 | 서버를 여러 대 띄우거나 재시작해도 지켜진다 |
| 8 | 알림 대기열은 `FOR UPDATE SKIP LOCKED` 로 집는다 | 단일 서버 가정 | 서버가 여러 대여도 같은 알림을 두 번 보내지 않는다 |
| 9 | 작성자 ID는 소금 친 SHA-256 해시로만 저장 | 원본 ID 저장 | 같은 사람의 반복 제보는 알 수 있으면서 개인 식별 정보를 DB에 남기지 않는다 |
| 10 | 슬랙 버튼 요청은 서명(HMAC)과 5분 시각 제한을 확인한 뒤, 관리자 슬랙 ID 목록에 있을 때만 상태 변경 | 버튼 값만 믿고 처리 | 서명이 없으면 누구나 상태를 바꾸는 요청을 위조할 수 있다 |
| 11 | 디스코드 라이브러리 이벤트는 얇은 연결층에서 `DiscordInbound` 로 바꿔 처리기로 넘긴다 | 리스너 안에 접수 로직 | 실제 디스코드 없이 처리 로직을 전부 테스트할 수 있다 |
| 12 | 관리자 API 키는 상수 시간 비교, 빈 키는 무시 | 문자열 equals | 응답 시간 차이로 키를 추측하는 공격을 막고, 설정이 비어 있을 때 아무나 통과하는 사고를 막는다 |
